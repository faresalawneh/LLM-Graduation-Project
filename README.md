# INFERSCOPE

Observability for a vLLM inference server, wired so that application-level
serving metrics (time to first token, request latency, output throughput) and
GPU hardware telemetry (SM clock, framebuffer usage, power, temperature) land
in the same Prometheus instance and the same Grafana view.

Load is generated by replaying real request arrival patterns from the BurstGPT
dataset. Two 15-minute windows are committed as trace files: a steady window
(72 requests) and a burst window (9,483 requests). AIPerf replays a window
against vLLM at its original inter-arrival times and streams per-batch metrics
over OTLP/HTTP during the run, so the dashboards update live rather than only
at the end. Each completed run is logged to a local MLflow store with its
parameters, metrics, artifacts, and the vLLM container's crash/restart state.

A separate FastAPI service exposes the same Prometheus data over REST with JWT
auth and two roles.

This is a Graduation Project at Jordan University of Science and Technology,
Faculty of Computer and Information Technology.

## Problem statement, objectives and scope

### Problem statement

Serving a large language model on a single GPU is hard to operate blind: when request
traffic bursts, time to first token (TTFT) and request latency can degrade by orders of
magnitude within minutes, and the cause (queueing in the serving engine versus GPU
saturation) is only visible if application-level serving metrics and GPU hardware
telemetry are viewed together. INFERSCOPE is an observability stack for a vLLM inference
server that replays real request arrival patterns (BurstGPT) and brings TTFT, request
latency, output throughput, vLLM scheduler state and GPU telemetry (SM clock, framebuffer
usage, power, temperature) into one Prometheus instance and one Grafana view, with every
run logged to MLflow, so that an operator can see, compare and reproduce load-induced
degradation on one machine.

### Measurable objectives

| # | Objective | Metric | Target | How measured |
|---|---|---|---|---|
| O1 | Unified, near-live visibility | Event-to-panel delay: time from a request completing to the value appearing on the Grafana vLLM dashboard | <= 20 s (5 s scrape + 10 s dashboard refresh + margin) | During a smoke run, compare AIPerf per-request completion timestamps with the first Grafana/Prometheus sample that reflects them; report the median and max over 10 events |
| O2 | Complete telemetry coverage | Share of required series that have >= 1 sample per 15 s throughout a steady run. Required: ttft_ms, request_latency_ms, throughput_tokens_per_sec, vllm:* scheduler gauges, DCGM_FI_DEV_SM_CLOCK, DCGM_FI_DEV_FB_USED | 100% of required series. Power and temperature best effort; PCIe panel documented as unsupported on WSL2 | Prometheus range queries over the run window, checked by a script, result stored in the MLflow run |
| O3 | Characterized steady-load latency | TTFT p95 and request latency p95 for the 72-request steady window | TTFT p95 <= 1,000 ms (to be confirmed against the first full AIPerf baseline; the legacy path measured 509 ms average TTFT) | `profile_export_aiperf.csv` p95 rows, logged as MLflow metrics |
| O4 | Degradation is visible before it is severe | Lead time between a leading indicator (vllm:num_requests_waiting above a set threshold) and TTFT first exceeding the SLO, on the 9,483-request burst window | Lead time >= 5 s in the burst run; steady run has zero false alarms | Offline analysis of `server_metrics_export.csv` (333 ms polling) against per-request TTFT in `profile_export.jsonl` |
| O5 | Reproducible, trustworthy runs | (a) Coefficient of variation of TTFT p95 across 3 repeat steady runs. (b) Runs with an unflagged vLLM restart/OOM | (a) CoV <= 15%. (b) 0: any restart is recorded in MLflow (`vllm_restarts_during_run`) and the run is marked invalid | Repeat `./run_experiment.sh steady` three times; compare MLflow runs; check restart metrics |

### MVP scope

**In scope**
- One machine, one GPU, one model (Qwen2.5-1.5B-Instruct) served by vLLM
- Trace replay of two committed BurstGPT windows (steady: 72 requests, burst: 9,483) through AIPerf
- Prometheus, OpenTelemetry collector, NVML-based GPU exporter and two Grafana dashboards (vLLM serving, GPU telemetry)
- MLflow run logging with restart/OOM detection
- Read-only FastAPI service with JWT auth and two roles exposing the same metrics
- Reproduction instructions in the README

**Out of scope**
- Multi-GPU, multi-node or multi-model serving
- Serving engines other than vLLM
- Automated remediation (load shedding, autoscaling, request routing)
- A trained prediction model for degradation (O4 uses a threshold-based leading indicator only)
- DCGM profiling counters (`DCGM_FI_PROF_*`) and anything requiring DCGM on WSL2
- Production hardening (a secrets manager, multi-user accounts, TLS, HA Prometheus)
- Alerting integrations (email, Slack, PagerDuty)

## Architecture

```
  monitoring/scripts/steady_window.csv        (BurstGPT 900s window, Git LFS)
  monitoring/scripts/burst_window.csv
              |
              v
  +-----------------------------+
  |  aiperf profile             |   --custom-dataset-type burst_gpt_trace
  |  (aiperf_trace_replay.py)   |   --fixed-schedule --streaming
  +-----------------------------+
       |                |
       | HTTP           | OTLP/HTTP :4318/v1/metrics
       | requests       | (per-batch, during the run)
       v                v
  +----------+    +-------------------+
  |  vLLM    |    |  otel-collector   |  histogram sum/count -> running mean,
  |  :8000   |    |  :4318 in         |  seconds -> ms, adds scenario label
  |          |    |  :8889 out        |  -> ttft_ms, request_latency_ms,
  +----------+    +-------------------+     throughput_tokens_per_sec
       |                |
       | /metrics       | /metrics
       |  (vllm:*)      |
       v                v
  +---------------------------------------+       +------------------+
  |            Prometheus :9090            |<------|  nvml-exporter   |
  |  jobs: vllm, otel_collector,           |       |  :9400           |
  |        dcgm_exporter                   |       |  DCGM_FI_DEV_*   |
  +---------------------------------------+       +------------------+
       |                        |
       v                        v
  +--------------+     +-----------------------+
  | Grafana :3000|     | api/app.py :5000      |
  | 2 dashboards |     | FastAPI + JWT         |
  +--------------+     +-----------------------+

  after the run:
  artifacts/<scenario>_<timestamp>/  --(mlflow_log_run.py)-->  mlruns/mlflow.db
```

Data flow notes that are easy to get wrong:

- AIPerf does not push to a Pushgateway. It streams OTLP to the collector, and
  the collector is what Prometheus scrapes. There is no Pushgateway service in
  `monitoring/docker-compose.yml`.
- The GPU exporter emits `DCGM_FI_DEV_*` metric names but is NVML-based. See
  Known issues.
- `monitoring/scripts/burstgpt_real_replay.py` is a legacy second path that
  bypasses AIPerf entirely and does push to a Pushgateway. It does not run
  against the current stack unmodified.

## Hardware and environment requirements

The stack as committed targets one machine: a laptop with an NVIDIA RTX 5060
Laptop GPU (8 GB, Blackwell, sm_120) under WSL2 with Docker Desktop.

| Requirement | Value |
|---|---|
| GPU | NVIDIA, CUDA-capable, at least 8 GB VRAM for Qwen2.5-1.5B-Instruct at `--gpu-memory-utilization 0.85` |
| Driver | NVIDIA driver with WSL2 GPU support; the container runtime bind-mounts `libnvidia-ml.so` into the exporter |
| Container runtime | Docker with the NVIDIA container runtime (`driver: nvidia` device reservations are used by the vllm and nvml-exporter services) |
| Python | 3.12 (CI runs 3.12; `requirements-experiments.txt` pins are verified on 3.12). `api/Dockerfile` and `Dockerfile.nvml` both build on 3.12 |
| Disk | Hugging Face model cache lives in the `hf_cache` Docker volume (`monitoring_hf_cache` for dev, `inferscope-demo_hf_cache` for the demo, so the demo downloads the model once on its first start); a burst run's artifact directory plus its MLflow copy is on the order of a few hundred MB. `burst_window.csv` is 392 KB over Git LFS |
| RAM | Not pinned anywhere in the repo |

DCGM vs NVML: NVIDIA's DCGM Exporter cannot run under WSL2, because the GPU is
paravirtualized and `nv-hostengine` will not start. `monitoring/exporters/nvml_exporter.py`
reads the same fields directly from NVML and re-emits them under the exact DCGM
metric names and labels (`gpu`, `UUID`, `modelName`, plus `source="nvml"`) on the
same port 9400, so Prometheus and the Grafana dashboards work unchanged. Only
`DCGM_FI_DEV_*` gauges are covered. `DCGM_FI_PROF_*` profiling counters are
DCP-family only and do not exist on this path, which is why the PCIe throughput
panel in the GPU dashboard shows a note instead of data. Power and temperature are frequently
unsupported under WSL2; each field is probed individually and skipped rather
than failing the whole scrape.

## Quickstart

### 1. Clone and materialize the LFS traces

The trace CSVs are stored in Git LFS. Without this step they are 130-byte
pointer files and every replay fails.

```bash
sudo apt-get install -y git-lfs && git lfs install --skip-repo
git clone https://github.com/faresalawneh/LLM-Graduation-Project.git
cd LLM-Graduation-Project
git lfs checkout
wc -l monitoring/scripts/steady_window.csv   # should be ~73, not 3
```

### 2. Python environment

`run_experiment.sh` and `mlflow_ui.sh` look for a venv at `~/venvs/aiperf-env`
(override with `AIPERF_VENV`).

```bash
python3.12 -m venv ~/venvs/aiperf-env
source ~/venvs/aiperf-env/bin/activate
pip install -r requirements.txt
pip install "aiperf[otel]"                    # see Known issues
pip install -r requirements-experiments.txt   # mlflow, only if you want run tracking
```

### 3. Create `monitoring/.env`

`monitoring/.env` is gitignored. Copy the committed template, which pins every
image to an exact version. `stack_up.sh` refuses to start if `VLLM_IMAGE` is
unset or ends in `:latest`.

```bash
cp monitoring/.env.example monitoring/.env
```

Then set `GRAFANA_ADMIN_PASSWORD` in it; compose will not start Grafana
without one.

### 4. Start the stack

```bash
cd monitoring
./stack_up.sh
```

This is the dev environment: it builds `nvml-exporter` locally. For the
assessed version, see [Dev and demo environments](#dev-and-demo-environments).

This runs `docker compose --profile local up -d` (Prometheus, otel-collector,
Grafana, nvml-exporter, vLLM), starts a `docker events` watcher writing to
`monitoring/logs/vllm_events.jsonl`, polls `http://localhost:8000/v1/models`
until the model loads (up to `VLLM_WAIT`, default 420s), and writes the image
digest and restart-count baseline to `monitoring/logs/stack_state.json`.

### 5. Run a replay

```bash
cd monitoring
./run_experiment.sh smoke      # 300 requests, ~30s,   artifacts -> /tmp/smoke_artifacts
./run_experiment.sh steady     # 72 requests,  ~15m
./run_experiment.sh burst      # 9,483 requests, ~15m
```

Run with no argument for an interactive menu. `--teardown` stops the stack
afterwards; `--no-mlflow` skips the MLflow logging step. The script starts the
stack itself if vLLM is not already answering.

To run the replay directly, without the wrapper, MLflow logging, or the crash
check:

```bash
cd monitoring/scripts
./run_local_replay.sh steady    # or: burst
```

### 6. Check health

```bash
curl -sf http://localhost:8000/v1/models   # vLLM
curl -sf http://localhost:9090/-/healthy   # Prometheus
curl -sf http://localhost:9400/metrics     # GPU exporter
curl -s  http://localhost:8889/metrics | grep ttft_ms   # collector output, during/after a run
```

Grafana is at `http://localhost:3000` (user `admin`, password `GRAFANA_ADMIN_PASSWORD`), with both dashboards
provisioned automatically. Prometheus target health is at
`http://localhost:9090/targets`.

### 7. View results

```bash
cd monitoring
./mlflow_ui.sh          # http://localhost:5000
./mlflow_ui.sh 5001     # alternate port
```

In the UI, toggle "Model training" (not GenAI) at top left, then open the
`inferscope-gp2` experiment.

### 8. Run the API

Set the API credentials once (see
[Identity management and roles](#identity-management-and-roles)):

```bash
cp api/.env.example api/.env   # then fill in JWT_SECRET and both passwords
```

Start the monitoring stack first (step above), then:

```bash
docker compose -f api/docker-compose.yml up -d
curl -s http://localhost:5000/health
```

`api/docker-compose.yml` joins the monitoring compose network
(`monitoring_monitoring`, the name compose gives it when the stack is started
from `monitoring/`) and sets `PROMETHEUS_URL=http://prometheus:9090`. If you
started the stack under a different project name, set `MONITORING_NETWORK`
(the demo stack uses `inferscope-demo_monitoring`).
It pulls the image CI publishes from `main`,
`mahmoudalwaqfi/llm-observability-api:latest` (override the account with
`DOCKERHUB_NAMESPACE` and the tag with `API_IMAGE_TAG`).
Without the monitoring stack the network does not exist and `up` fails; to run
the API alone on the host use
`PROMETHEUS_URL=http://localhost:9090 python api/app.py` instead. It reads `api/.env` too.

Swagger UI is at `http://localhost:5000/docs`. Alert thresholds are a full CRUD
resource at `/thresholds` (POST/GET for any logged-in user, PUT/DELETE admin
only; stored in memory, so they reset when the container restarts):

```bash
TOKEN=$(curl -s -d "username=admin&password=$API_ADMIN_PASSWORD" http://localhost:5000/auth/token | jq -r .access_token)
curl -s -X POST http://localhost:5000/thresholds -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name":"High TTFT","metric":"ttft_ms","operator":">","value":500}'
```

### 9. Test the API (Swagger and Postman)

Users are `admin` (all endpoints) and `viewer` (no `/gpu`, `/vllm`, or
threshold PUT/DELETE; those return 403), with the passwords you set in
`api/.env`. The Postman `local` environment expects `admin123` / `viewer123`;
change it there if you chose other passwords.

**Swagger.** Open `http://localhost:5000/docs`, click **Authorize**, enter a
username and password (leave client id/secret empty), then use **Try it out**
on each endpoint. Log out and repeat as the other user.

**Postman.** `api/postman/` holds a collection (32 requests, 59 assertions) and
a `local` environment (`baseUrl`, credentials). Import both, select the
environment and run the whole collection in order: it logs in as both users,
calls every endpoint, runs the threshold create/read/update/delete cycle, and
checks the 401/403/404/422 cases. The same run works from the command line and
runs in CI on every push:

```bash
npx newman run api/postman/llm-observability-api.postman_collection.json \
  -e api/postman/local.postman_environment.json
```

Metric values are `null` when Prometheus is not reachable; the tests check
status codes, field names and roles, not values. Change `baseUrl` in the
environment to test a remote deployment.

## Manual runs

`monitoring/scripts/start_run.py` is a gated front end for the dev environment.
Run it from the repository root. It needs `monitoring/.env` with `VLLM_IMAGE`
and `GRAFANA_ADMIN_PASSWORD`.

```bash
python3 monitoring/scripts/start_run.py --preflight                     # readiness checks
python3 monitoring/scripts/start_run.py --type smoke --dry-run          # print the plan only
python3 monitoring/scripts/start_run.py --type smoke                    # also: steady, burst
python3 monitoring/scripts/start_run.py --type steady --runs 3          # repeat a workload
python3 monitoring/scripts/start_run.py --type burst --no-mlflow        # skip MLflow logging
python3 monitoring/scripts/start_run.py --up                            # start the stack
python3 monitoring/scripts/start_run.py --down                          # stop it; volumes are kept
python3 monitoring/scripts/start_run.py --mlflow-ui                     # http://localhost:5001
```

`--type` and `--up` print a plan and continue only if you type exactly `yes`.
There is no bypass flag. `--type` calls `run_experiment.sh`, so a run starts the
stack if it is not already up. Starting the stack pulls any other missing
compose image and builds `nvml-exporter`.

`--preflight` does not run automatically before a run. It may start a
short-lived container from the already pulled vLLM image, with no GPU and no
network, to read the model cache. A zero exit code from a run does not rule out
a vLLM restart: check the crash check output.

What to change before running on a different machine:

| Item | Where | Note |
|---|---|---|
| Image versions | `monitoring/.env` (copy of `monitoring/.env.example`): `VLLM_IMAGE`, `PROMETHEUS_IMAGE`, `GRAFANA_IMAGE`, `OTEL_COLLECTOR_IMAGE` | Pinned in the template. `VLLM_IMAGE` is required and must not be `:latest` |
| Demo images | `monitoring/.env`, keys `DOCKERHUB_NAMESPACE` and `DEMO_IMAGE_TAG` | Demo only. The Docker Hub account CI pushes to, and the full commit SHA of the `gp2-demo` tag; the demo compose refuses to start without either |
| Model, `--max-model-len`, `--gpu-memory-utilization` | `monitoring/docker-compose.yml`, `vllm` service `command` | Currently `Qwen/Qwen2.5-1.5B-Instruct`, `4096`, `0.85`, `--dtype float16` |

| Concurrency | `monitoring/scripts/run_local_replay.sh`, `MAX_CONCURRENCY=20` | Fixed for comparability across runs. Same override caveat |
| GPU index in scrape queries | `aiperf_trace_replay.py` uses `gpu="0"`; `burstgpt_real_replay.py` uses `gpu="1"` | Edit to match the GPU you are serving on |
| Venv path | `AIPERF_VENV` env var, default `~/venvs/aiperf-env` | Honoured by `run_experiment.sh` and `mlflow_ui.sh`. `run_local_replay.sh` only prints this path in its error message and requires `aiperf` already on PATH |
| MLflow host tag | `monitoring/scripts/mlflow_log_run.py`, `"host": "msi-rtx5060-wsl2"` | Hardcoded on every run |
| Prometheus URL used by the API | `PROMETHEUS_URL` env var, default `http://localhost:9090` | `api/docker-compose.yml` sets it to `http://prometheus:9090` and attaches the API to the monitoring network (`MONITORING_NETWORK`, default `monitoring_monitoring`). `prometheus`, `grafana`, ...) are fixed. `stack_up.sh` stops with a message if
the other environment's containers still exist. Bring that environment down


`/tmp/smoke_artifacts`. If two runs start in the same minute, a numeric suffix
is appended.

| File | Written by | Format |
|---|---|---|
| `run_manifest.json` | `aiperf_trace_replay.py` | JSON: scenario, model, endpoint type, trace path, row count, slice duration, tokenizer, OTel URL, GPU scrape flag, start time |
| `profile_export_aiperf.csv` | AIPerf | Summary CSV, one row per metric with avg/min/max/p50/p95/p99. Parsed by `run_experiment.sh` and `mlflow_log_run.py` |
| `profile_export.jsonl` | AIPerf | Per-request records, flushed at end of run |

## Known issues and gotchas

**`--otel-url` must carry the full `/v1/metrics` path.** AIPerf 0.11 does not
append the OTLP path. With a bare `http://host:4318` URL it exports nothing:
no error, no metrics on :8889, empty Grafana panels. The correct value is
`http://localhost:4318/v1/metrics`, which is what `run_local_replay.sh` exports
and what `aiperf_trace_replay.py` defaults to.

**OTel streaming needs the `otel` extra.** `requirements.txt` pins plain
`aiperf==0.11.0` and contains no `opentelemetry-*` packages. Install
`aiperf[otel]` separately or `--stream metrics` will not work.

**`VLLM_IMAGE` must be pinned.** `stack_up.sh` exits if the tag is missing or
ends in `:latest`, because the current `:latest` image dies on this Blackwell
GPU with UVA unavailable. Copy `monitoring/.env.example` to `monitoring/.env`
on a fresh clone; the template already pins it.

**Trace CSVs are Git LFS pointers.** Without `git lfs checkout` they are
130-byte text files and `aiperf` will read a nonsense trace. A checkout can
also re-materialize them with CRLF line endings; `run_local_replay.sh` strips
those in place before each run.

**DCGM cannot run under WSL2.** `nvml-exporter` stands in for DCGM Exporter on
port 9400 with the same metric names. `DCGM_FI_PROF_*` counters do not exist on
this path, so the PCIe panel in the GPU dashboard shows a note instead of data, and power
and temperature may be missing depending on driver support.

**Only the `local` profile exists.** Services with no profile (Prometheus,
otel-collector, Grafana) start regardless of the flag.

**Pushgateway does not expire metrics.** The legacy `burstgpt_real_replay.py`
pushes gauges that persist until explicitly deleted, so a stale run's values
keep being scraped and mix into the next run's panels. This is one reason the
Pushgateway was dropped from the stack. The service is no longer in
`docker-compose.yml`, and the `docker/pushgateway/Dockerfile` image was removed
in #29. The legacy script still points at :9091; to run it, start the official
`prom/pushgateway` image and add a matching Prometheus scrape job.

**`burstgpt_real_replay.py` has Windows-absolute defaults.** `DATASET_PATH` and
`ARTIFACT_ROOT` default to `C:\Users\alawn\...`. Both must be overridden on any
other machine.

**GPU index is inconsistent between the two replay scripts.** The current path
queries `gpu="0"`, the legacy one `gpu="1"`. If the GPU scrape logs
"GPU scrape missing", this is the first thing to check.

**MLflow's Duration column is logging time, not benchmark time.** Use the
`wall` figure printed by `run_experiment.sh`.

**MLflow UI and the API both default to port 5000.** Run one or the other, or
pass an alternate port to `mlflow_ui.sh`.

**`run_local_replay.sh` uses `export`, not defaults.** `MODEL`,
`INFERENCE_URL`, `MAX_CONCURRENCY`, `ENABLE_GPU_SCRAPE` and others are set
unconditionally, so exporting them in your shell before calling the script has
no effect. Edit the script instead. `TRACE_FILE` and `ARTIFACT_ROOT` are the
exceptions and do honour the environment.

**vLLM restarts silently.** The service has `restart: unless-stopped`, so a
crash mid-run looks like a gap in the data rather than a failure.
`stack_up.sh` records a restart-count baseline and `run_experiment.sh` compares
against it afterwards; a nonzero delta means the results for that run are
suspect. Details land in `monitoring/logs/vllm_events.jsonl`.

**Committed build noise.** Five `__pycache__/*.pyc` files are tracked, two of
them for scripts that no longer exist (`aiperf_with_push.py`,
`aiperf_live_grafana.py`). `.idea/` is also tracked.

### Identity management and roles

The API issues its own JWTs (HS256, OAuth2 password flow at `/auth/token`). We
considered Microsoft Entra ID and decided to keep JWT for the MVP: the API has
two fixed roles and runs on a single laptop, so an external identity provider
adds setup without changing what the API protects.

| Role | Can do | Gets 403 on |
|---|---|---|
| `admin` | Everything (`require_role` lets admin through every role check) | Nothing |
| `viewer` | `/metrics/summary`, create/list/get thresholds | `/gpu`, `/vllm`, `PUT` and `DELETE /thresholds/{id}` |
| no token | `/`, `/health`, `/docs`, `/auth/token` | 401 on everything else |

A request gets **401** when the token is missing, expired, signed with another
key, edited after signing, uses `alg: none`, or lacks a valid `sub`/`role`
claim. It gets **403** when the token is valid but the role is not allowed.
`api/test_auth.py` checks every cell of this table and every rejection case,
and fails if this README table and the routes in `app.py` drift apart.

**Configuration.** No credentials are in the source. `api/auth.py` reads them
from the environment, or from `api/.env` when you run `python app.py` on the
host (copy `api/.env.example`; `api/.env` is gitignored):

| Variable | Purpose | If unset |
|---|---|---|
| `JWT_SECRET` | HMAC signing key, at least 32 characters | A random key per process: tokens stop working after a restart |
| `API_ADMIN_PASSWORD` | Password for user `admin` | Admin login disabled |
| `API_VIEWER_PASSWORD` | Password for user `viewer` | Viewer login disabled |
| `JWT_EXPIRE_MINUTES` | Token lifetime | 60 |

Generate a secret with
`python -c "import secrets; print(secrets.token_urlsafe(48))"`. Passwords are
bcrypt-hashed when the API starts; only the hash is kept in memory. The tests
and CI use `admin123` / `viewer123`, which are also the values in the Postman
`local` environment.
